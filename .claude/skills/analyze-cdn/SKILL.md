# /analyze-cdn [國家代碼]

把 `/collect-speedtest-mail` 存下的各份 `*-summary.json` 合起來看，產生一份**分析報告**給使用者讀，使用者再決定怎麼處理。
**這個技能不改任何專案檔案、不刪任何報告**：更新 `src/cdn-list.json`（第 5 節）、刪除報告資料夾，都要等使用者讀完報告明確說了才做。
不管樣本多少都要給建議，只在報告裡標清楚信心等級。

以下 `$SK` = `.claude/skills/analyze-cdn`，`$R` = `cdn-speedtest-results`（gitignored，含出口 IP），都在 repo 根目錄執行。腳本只用 Python 標準函式庫，一律 `python -I`。

## 目標（腳本與判讀都以此為準）

1. **預設節點**：在擴充還沒有「依 ISP 選節點」之前，**最大化使用者剛安裝時預設節點就能順暢播 4K 的機率**。
   預設不必最快，但要最穩、最不會出錯。
2. **剩餘 9 個節點**：讓同一國任何 ISP 的使用者，都有最大機率能在清單裡找到適合自己 ISP、能順暢播 4K 的節點。

## 1. 準備

1. 國家代碼沒給：`ls $R` 列出各國份數，問使用者要分析哪一國。
2. 使用者可能有新的測速信還沒收：提醒可以先跑 `/collect-speedtest-mail`（不要自己決定跑）。
3. **市占資料** `$SK/isp-share.json`：預設節點的覆蓋率要用各 ISP 的固網寬頻市占加權，市占**必須來自網路統計**（NCC／監管機關、Opensignal、業者財報），**不能從收到的報告數量推**。
   - 該國沒有資料、或 `asof` 超過 2 年：先 WebSearch 查「<國家> 固網寬頻 市占／用戶數」，把各 ISP 的 `share`（0–1）、`match`（報告裡會出現的 ASN 或 ip-api `isp` 名稱片段）、`sources`（含年份）寫進去，再跑腳本。對不到市占的 ISP 會用 `other_each`。
   - 報告裡出現了檔案沒對應到的 ISP（報告第 1 節會標 ⚠ 未對應）：查它屬於哪家（子公司、品牌）補進 `match`；真的是小 ISP 就留給 `other_each`。
   - 同一家對到多個 ASN（例如遠傳 + Seednet）腳本會把市占平分。

## 2. 產生報告

```bash
python -I $SK/analyze.py <國家> [--exclude rid,...] [--include rid,...]
```

輸出 `$R/_analysis/<國家>-<yyyymmdd-HHMM>.md`（分析報告，不含 IP）與同名 `.json`（建議清單與要問的報告，第 4、5 節用），最後一行 `OUTPUT <路徑>`。

腳本做的事（報告裡都有寫明規則，回報時不必重述）：

- **線路**：同 ISP 且同出口 IP（或同 /24、同網卡）的報告是同一戶的重複測試，合併成 1 個樣本。IP 只在記憶體比對，不寫進報告。
- **達標**：單連線平均速度 ≥ 90% × min(25 Mbps, 該報告最快穩定節點) = 跑得動 4K。不穩定（sd > 平均一半）、細測失敗、快篩失敗、只能播熱門（403）、冷門片探測失敗都是不達標。沒進細測但有快篩速度（新版 GUI 的 `stage1.nodes`）用快篩速度判斷；完全沒量到 = 不知道。
- **新版報告（有 `stage2.raw` 逐筆紀錄）**：細測有失敗的節點若成功率 ≥ 80% 且失敗都不是 403 → 「部分失敗」：速度用成功那幾支算，分級比照不穩定打五折再乘成功率（最多到「可用」），**達標仍算 0**（預設要最不會出錯）。成功率更低或有 403 → 照舊算失敗。另從 cache miss 的那幾支算「冷門片 Mbps」在候選表顯示。舊版報告沒有 raw，自動退回原本的判讀。報告第 1 節會寫有幾份是新版。
- **自動排除**量測本身壞掉的報告（快篩通過 < 30 個 = DNS 或網路異常、上限 < 30 Mbps）。`--include` 可強制納入、`--exclude` 可人工排除。
  細測成功少但快篩正常**不排除**：那多半是這家網路對多數節點就是 403／逾時（例如台灣 TBC），是真實體驗；只提示「排名基礎薄」。
- **量測設定提示**只列客觀事實（同線路 24 小時內 ≥ 3 份、並行數手動改過、未登入），腳本不下「疑似測試」的結論，也不自動排除。
- **離群報告**：與其他線路共識的 Spearman 相關明顯偏低；再看同 ISP 其他線路是否也一樣 → **ISP 通案**（該 ISP 的真實體驗，保留）或**個案**。
- **預設候選（覆蓋率）**：每個節點算 Σ(ISP 市占 × 該 ISP 各線路達標比例的平均) ÷ Σ(有報告的 ISP 市占)。
  - 同一線路多份報告取平均，所以單筆極端值只佔該線路的一部分，不會直接否決；沒量到的報告算 0.5（只在該 ISP 至少有一條線路量到時）；整個 ISP 都沒量到算 0。
  - **第一步**：有節點在所有 ISP 的所有報告都達標、沒有未知（覆蓋 100%）→ 只列這些，先排沒有穩定疑慮的，再依平均速度。
  - **退路**：沒有 → 依覆蓋率排序（市占大的 ISP 權重大，所以通常會落在最大 ISP，但其他 ISP 合計更大時也會反映），同覆蓋率先排穩定的、再依平均速度。
  - 穩定條件：無不穩定／失敗紀錄、速度波動（sd/平均中位）≤ 0.3、TTFB ≤ 1000 ms。每個候選列入選原因、哪些 ISP／線路／報告未達標、是單筆波動還是線路個案。
- **剩餘 9 個**：每家 ISP 只用自己的線路分級（第一梯隊／可用／差）。依市占順序輪流取每家第一梯隊中最好的一個，再取第二好的，直到 9 個；已選過的跳過；第一梯隊取完才用「可用」補，仍不足就少列。
  - **冗餘不重複取**：候選節點若對這家 ISP 來說與清單裡任何已選節點（含預設、含別家 ISP 選的）冗餘，就跳過。冗餘 = 在該 ISP 的報告裡兩者達標結論一致率 ≥ 90%、且至少一份同時達標（兩者都有結論的報告 ≥ 3 份）。資料不足或兩者從沒同時達標時，退回「同機房」（`cn-*`／`ec-*` 去末碼的前綴）當先驗。
  - 為什麼這樣分：單一 ISP 看一個機房 = 同一條路徑，同機房節點表現幾乎相同（單份報告內速度離散度 0.02–0.1、達標結論 80–100% 一致），但 `cn-hk-eq-01`、`cn-gddg-cu-01` 是例外，所以有數據就用數據。**全國層面不用機房分池**：跨報告真正一起好一起壞的是 ISP 陣營（台灣：不同機房的 `cn-hbwh`／`cn-sdjn`／`cn-bj-se` 100% 同好同壞），多樣性靠「每個 ISP 都取到」保證。機房前綴另外是故障單位（機房離線）的分散依據，這點測速資料測不到。輪取過程每一次跳過都附依據。
- **樣本**：< 3 條線路「不足」、3–5「偏少」、≥ 6「尚可」（全國與各 ISP），另列沒有報告的主要 ISP、時段缺口、以線路重抽樣的入選率與「當預設比例」。
- **清單對各 ISP 的照顧**：每家 ISP 在建議清單與目前清單裡最好的節點，看有沒有 ISP 被漏掉。

## 3. 判讀（Claude 要做的事）

讀整份報告（不含 IP，可以讀進上下文；**不要**讀原始 `summary.json` 的 `env.exit.ip` 等欄位）。逐項檢查，必要時調整 `--exclude`／`--include` 重跑：

- **第 2 節「要問使用者的報告」**：
  - 已自動排除的：看理由合理嗎（DNS 壞掉、細測太少）。合理 → 列入「建議刪除」；其實可用（例如只是節點少但數據一致）→ `--include` 重跑並說明。
  - 是不是測試報告：**只能**依量測設定（並行數手動改過、未登入、DNS 改道、`--limit-nodes`）或使用者自己說「那是我在測」來判定。不同出口網段、不同網卡、不同城市 = 不同使用者；同一 ISP 多份報告一致地差（403 多、細測成功少、速度低）是該 ISP 的真實體驗，**不是測試，也不要因為「看起來太差」排除**。拿不準就列出特徵問使用者，不要自己下結論。
  - 個案離群且有量測疑點（並行數手動、互搶頻寬、DNS 改道）、而且拿掉它會改變預設或清單 → `--exclude` 重跑；**ISP 通案不要排除**。
- **極端值**：第 3 節候選的未達標明細標了「單筆波動」「線路個案」。單筆波動已被平均稀釋，不必處理；若某條線路對幾乎所有節點都是 0（量測問題），考慮排除那份報告；若某節點只在單一 ISP 的單一線路崩潰、其他線路都好，在判讀寫明這是個案、不據以換掉預設。
- **預設**：確認第一名的覆蓋率沒有被「未知算 0.5」撐起來（看「已知」欄與各 ISP 欄的未知數）；若第一名靠未知撐場、第二名已知覆蓋更紮實，判讀裡建議第二名並說明。第一步不成立時，寫清楚預設對哪些 ISP 的使用者會不順、占多少市占。
- **清單**：對照「清單對各 ISP 的照顧」，每家 ISP 至少要有一個第一梯隊；單線路 ISP 的第一梯隊全是 1.00 同分，名次不可信，說明這點。
- **樣本**：「不足」時判讀第一句就寫「樣本不足，建議僅供參考」；列出沒有報告的主要 ISP（市占）與該補的樣本。
- 數據看起來不合理（某池全部 0、某份大量 DNS 失敗）時，回頭看該報告的 `REPORT.md` 再判斷，不要硬套規則。

然後用 Edit 把報告最後的 `<!-- CLAUDE: … -->` 換成「## 7. 判讀」的內文（繁體中文、條列為主），涵蓋：

1. **結論一句話**：建議的預設與清單、信心等級（樣本尚可／偏少／不足）。
2. **預設節點**：第一步是否成立；候選前 3 名與理由（覆蓋哪些 ISP、速度、穩定）；覆蓋不到的 ISP 與其市占；若建議的不是腳本第一名，說明原因。
3. **要問使用者的報告**：建議刪除哪些（理由）、保留哪些（理由）；有用 `--exclude`／`--include` 重跑時說明對結果的影響。
4. **剩餘節點**：各 ISP 分到哪些、和目前清單相比換掉哪些、為什麼。
5. **各 ISP 的照顧與風險**：哪些 ISP 只有一條線路、哪些主要 ISP 完全沒報告、哪些名次入選率 < 50%。
6. **待補樣本**：ISP／時段／城市。

有重跑時，舊的報告檔（同國家較早時間的 `.md`／`.json`）刪掉，只留最後一份。

## 4. 回報

告訴使用者報告路徑，並用幾行摘要：結論、預設與候選、樣本狀況、主要變動。然後**明確列出要使用者決定的事**：

1. **要不要刪除**第 2 節列出的報告資料夾（逐份列 rid、ISP、理由、路徑）。
2. **要不要更新** `src/cdn-list.json`。

**明確說「尚未修改任何檔案、尚未刪除任何報告，讀完報告後告訴我」**，然後停下來等使用者。

## 5. 使用者決定後

### 刪除報告（只刪使用者點名的）

`rm -r $R/<國家>/<報告資料夾>`，刪完重跑第 2 節讓報告反映最新狀態。

### 更新節點庫（只在使用者明確要求後）

1. 讀最新的 `$R/_analysis/<國家>-*.json`：`nodes`（第一個是預設）、`not_in_options`。使用者對清單有修改意見就照使用者的。
2. 改 `src/cdn-list.json`：
   - `countries` 中該國的 `nodes` 換成新清單（第一項 = 預設）。
   - 國家還不存在：新增 `{ "code", "dial", "name": {zh_TW, zh_CN, en, ja, ko} }`，`dial` 是國際電話區碼（對應 B 站 zone API 的 `country_code`），名稱五語都要寫。
   - `not_in_options` 的節點要加進 `options`（`value`、`name` 技術代號、`pool` 對應 `pools` 的 key；新池要在 `pools` 補五語標籤）。
   - 確認 JSON 合法：`node -e "JSON.parse(require('fs').readFileSync('src/cdn-list.json','utf8'))"`。
3. 這是使用者感受得到的改動：依 `agent.md` 在 `src/changelog.json` 的 `unreleased` 追加一條 `fix` 或 `feature`（五語，寫給使用者看，例如「更新台灣的建議節點清單與預設節點，依實測改用較快的節點」），再 `npm run changelog:validate`。
4. 給使用者看 diff；commit／push 只在使用者要求時做，並遵守 `agent.md` 的 commit 規則（作者 `John H`、不加 AI 署名）。
